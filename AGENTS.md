## Overview

macOS menu bar companion app. Lives entirely in the macOS status bar (no dock icon, no main window). Clicking the menu bar icon opens a custom floating panel with companion voice controls. Uses push-to-talk (ctrl+option) to capture voice input, transcribes it with Apple Speech (this fork's provider; AssemblyAI streaming and OpenAI are the alternatives), and sends the transcript + a screenshot of the user's screen to Claude. Claude responds with text (streamed via SSE) and voice (ElevenLabs TTS, played as it streams in). A blue cursor overlay can fly to and point at UI elements Claude references on any connected monitor.

All API keys live on a Cloudflare Worker proxy — nothing sensitive ships in the app.

## Architecture

- **App Type**: Menu bar-only (`LSUIElement=true`), no dock icon or main window
- **Framework**: SwiftUI (macOS native) with AppKit bridging for menu bar panel and cursor overlay
- **Pattern**: MVVM with `@StateObject` / `@Published` state management
- **AI Chat**: Claude (Sonnet 5.5 default, Opus 5.5 optional, both at low effort) via Cloudflare Worker proxy with SSE streaming. `ClaudeVoiceModel` in `ClaudeAPI.swift` holds the model IDs, and a choice saved by an older version moves to the latest model of its family. Use only the latest model of each family.
- **Prompt caching**: the app marks a cache breakpoint on the `/chat` system prompt (`ClaudeAPI.streamingRequestBody`), and the Worker puts one on the system prompt of every route that calls Anthropic, so later calls within 5 minutes read it at a tenth of the input price
- **Speech-to-Text**: Apple Speech, selected by `VoiceTranscriptionProvider` = `apple` in Info.plist. Setting it to `assemblyai` (real-time streaming over a websocket, `u3-rt-pro` model) or `openai` (upload on release) switches providers
- **Text-to-Speech**: ElevenLabs `eleven_v4_turbo` via Cloudflare Worker proxy, streamed as 24 kHz PCM and played as it arrives, so speech starts about 0.25 seconds after the request instead of after the whole line is generated
- **Screen Capture**: ScreenCaptureKit (macOS 14.2+), multi-monitor support
- **Voice Input**: Push-to-talk via `AVAudioEngine` + pluggable transcription-provider layer. System-wide keyboard shortcut via listen-only CGEvent tap.
- **Element Pointing**: Claude embeds `[POINT:x,y:label:screenN]` tags in responses. The overlay parses these, maps coordinates to the correct monitor, and animates the blue cursor along a bezier arc to the target.
- **Concurrency**: `@MainActor` isolation, async/await throughout
- **Analytics**: PostHog via `ClickyAnalytics.swift`

### API Proxy (Cloudflare Worker)

The app never calls external APIs directly. All requests go through a Cloudflare Worker (`worker/src/index.ts`) that holds the real API keys as secrets.

| Route | Upstream | Purpose |
|-------|----------|---------|
| `POST /chat` | `api.anthropic.com/v1/messages` | Claude vision + streaming chat |
| `POST /tts` | `api.elevenlabs.io/v1/text-to-speech/{voiceId}/stream` | ElevenLabs TTS audio, streamed. An `output_format` query such as `pcm_24000` passes through, and without one the audio is MP3 |
| `POST /transcribe-token` | `streaming.assemblyai.com/v3/token` | Fetches a short-lived (480s) AssemblyAI websocket token |
| `POST /live-scene` | `api.openai.com/v1/responses` | GPT-6.1 Sol Ultrafast, at medium reasoning effort, writes a three.js page and a quiz from the question and screenshot. The body takes `kind`, `"model"` (the default, so an older app still works) or `"simulation"`, which adds the simulation rules to the prompt and makes the reply check require the page's `controls`, `setControl`, `run`, and `readouts` |
| `POST /judge-answer` | `api.anthropic.com/v1/messages` | Sonnet grades a spoken answer as correct, named only, wrong, or a request for help, or hears a request to skip, repeat, get a hint, or change the view instead (`skip_question`, `repeat_question`, `wants_hint`, `scene_command`, where the skip, repeat, and scene command ones may have an empty `spokenReply`) |

| `POST /video-quiz-plan` | `api.anthropic.com/v1/messages` | Sonnet reads a video's timestamped transcript once, decides how many moments are worth a question, and picks them. | `POST /video-frame-parts` | `api.anthropic.com/v1/messages` | Sonnet finds the subject in a frame grabbed from the playing video, or a screen capture of a page image, and places up to 8 part labels, dropping any label that is not a short plain name. | `POST /picture-flows` | `api.anthropic.com/v1/messages` | Opus 5.5 (low effort) draws what flows through a popped-out picture, like air through an engine, and returns `{ flows: [{ color, style, points: [[x, y], ...] }] }` in frame pixels, with `color` one of blue, red, orange, cyan, green, yellow, or white, and `style` one of smoke, sparks, lava, droplets, air, current, or beads. Up to 6 flows of 12 points, clamped into the frame. Moving solid parts, like a bicycle chain, are not flows, so a picture of only those returns an empty list. The app never calls it for an artwork |
| `POST /study-guide` | `api.anthropic.com/v1/messages`, then `api.notion.com/v1/pages` | Sonnet drafts a study guide from a YouTube video's transcript as schema-checked JSON (`{ title, summary, sections: [{ heading, points: [{ text, seconds }] }], keyTerms }`), and the Worker writes it as its own private Notion page, with a "Review these first" section built from the quiz results the learner missed or skipped and a timestamp link on every point. A request with `revision` creates the new page, then trashes the old one. A `revision` with no `instruction` is a refresh: the Worker keeps the previous guide word for word, checks it like a model reply, and rebuilds the page with the new quiz results, with no model call. A transcript over 10,000 lines or 500,000 characters, any text field over 2,000 characters, or a handle over 200 characters gets a 400 before any model or Notion call. The prompt wraps the title, transcript, quiz results, and previous guide in `video_title`, `video_transcript`, `quiz_results`, and `previous_study_guide` tags, with every `<` in their text replaced so none can close its tag, and treats them as text to work from, never as instructions. 503 when `NOTION_API_KEY` is missing |
| `POST /study-guide-status` | `api.notion.com/v1/pages/{id}` | Whether a saved guide's page is still in Notion and out of the trash. | `POST /background-agent` | `api.anthropic.com/v1/messages` | One turn of a general task agent: Sonnet 5.5 at medium effort with Anthropic's web search and web fetch (6 uses each, fetched pages cut to 8,000 tokens) and the app's tools. The app sends `{ messages, tools }` and owns the loop. The reply is `{ content, stopReason }` with every block kept, thinking and server tool results included, since the next turn must send them back unchanged |
| `POST /notion-page` | `api.notion.com/v1/pages` | Writes a task agent's findings as a private Notion page from `{ title, summary, sections: [{ heading, points }], sources: [{ title, url }] }`, with https sources only, and returns `{ pageURL }`. 503 when `NOTION_API_KEY` is missing |
| `GET /v1/3dtiles/...` | `tile.googleapis.com` | Google Photorealistic 3D Tiles for the landmark page. Only `root.json` and dataset files pass, and the Worker adds `GOOGLE_MAPS_API_KEY` |

Worker secrets: `ANTHROPIC_API_KEY`, `ELEVENLABS_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_MAPS_API_KEY` (a Maps Platform key with the Map Tiles API enabled and billing linked), `NOTION_API_KEY` (a Notion personal access token, which acts as its owner and may create pages with no parent page, for study guides and task pages), `CLICKY_APP_SECRET` (a random string the app sends in `x-clicky-app-secret`, which `/study-guide`, `/study-guide-status`, `/notion-page`, and `/background-agent` require before any Notion or model call, with a constant-time compare in `worker/src/appSecret.ts`, answering 401 to a missing or wrong secret and to every request when the Worker has none), and `ASSEMBLYAI_API_KEY` only when Info.plist selects the `assemblyai` provider
Worker vars: `ELEVENLABS_VOICE_ID`, and optional `LIVE_SCENE_MODEL` (`gpt` by default, `sonnet`, `opus`, or `fable` for Claude Fable 5.2) and `LIVE_SCENE_EFFORT` (overrides the scene model's effort, which is `medium` for GPT and `low` for Claude, where GPT takes low, medium, or high)

### Key Architecture Decisions

**Menu Bar Panel Pattern**: The companion panel uses `NSStatusItem` for the menu bar icon and a custom borderless `NSPanel` for the floating control panel. This gives full control over appearance (dark, rounded corners, custom shadow) and avoids the standard macOS menu/popover chrome. The panel is non-activating so it doesn't steal focus. A global event monitor auto-dismisses it on outside clicks.

**Cursor Overlay**: A full-screen transparent `NSPanel` hosts the blue cursor companion. It's non-activating, joins all Spaces, and never steals focus. The cursor position, response text, waveform, and pointing animations all render in this overlay via SwiftUI through `NSHostingView`.

**Global Push-To-Talk Shortcut**: Background push-to-talk uses a listen-only `CGEvent` tap instead of an AppKit global monitor so modifier-based shortcuts like `ctrl + option` are detected more reliably while the app is running in the background.

**Shared URLSession for AssemblyAI**: A single long-lived `URLSession` is shared across all AssemblyAI streaming sessions (owned by the provider, not the session). Creating and invalidating a URLSession per session corrupts the OS connection pool and causes "Socket is not connected" errors after a few rapid reconnections.

**Interrupting a reply**: Escape or a quick ctrl+option tap stops the answer Clicky is thinking about or speaking, and a tap with no words asks nothing. With a scene or pop-out on screen, Escape keeps its scene behavior, and a tap stops the speech but leaves the scene up. Outside a video quiz question, Escape does nothing while a scene or pop-out is building or touring. Saying "put it back" or "put that away" (`asksToPutTheSceneBack`) sends a pop-out or explored scene back, during its tour or after it, unless a quiz question is waiting on it. A push-to-talk press sets a cancelled narration's responding state back to idle, so the listening waveform shows.

**Transient Cursor Mode**: When "Show Clicky" is off, pressing the hotkey fades in the cursor overlay for the duration of the interaction (recording → response → TTS → optional pointing), then fades it out automatically after 1 second of inactivity.

**Live Scene**: A transcript that contains "inside", "look like", "show me", "3D", or "render" calls `POST /live-scene`, and every label stays visible.
`POST /live-scene` asks GPT-6.1 Sol Ultrafast (`gpt-6.1-sol`, service tier `ultrafast`, medium reasoning effort) for a self-contained three.js page and a quiz. On a Starship frame, medium drew rounder, tiled ships than low for about $0.15 more and 2 to 4 more seconds, and high cost 4 times as much with no better ship.
The page builds the whole subject from the outside, and adds the parts inside, fading the outer shell, only when the learner asks to see inside.
The page imports three.js only from `clicky-asset://three/three.module.js`, which the overlay serves from the app bundle.
The overlay serves the generated page from `clicky-asset://live/page.html` with a Content-Security-Policy header, a content rule blocks http, https, ws, and wss, and navigation is limited to `about` and `clicky-asset`.
On a timeout, an error, or a 422, Clicky says "Sorry, I couldn't build that one." and resumes a video it paused for the scene.
A page that fails to load, or whose web content process ends, takes the same recovery as a page that throws: a quiz falls back to the voice-only question, and a scene says that line.
Only a failure of the load Clicky started counts (`pageLoadFailureEndsTheScene`), where that load is the `WKNavigation` that `load(_:)` returned, so a navigation the page starts itself, or one the policy refuses with WebKit error 102, leaves the scene on screen.
A transcript that says "quiz" or "test me" plays the same scene with one label shown as "?".
The overlay plays a generated scene on the screen under the mouse cursor.
A frame pop-out or landmark page plays on the screen showing its video or image instead, so it lines up even when the mouse is on another display.
The page rises out of the video or image it was asked about: Clicky reads the on-screen rect of the largest visible video or image in Chrome's front tab before the request, with a 2 second Apple Event timeout, since the tab can be any busy site, skipping images that show nothing (not loaded, hidden, or fully transparent), and places the rect from the web area in Chrome's accessibility tree, with the page-geometry math as the fallback when no web area matches, and `LiveSceneRise.swift` adds the cursor screenshot and that rect to the page for the bundled `scene-rise.js`, which shows the screenshot clipped to the rect and grows the page out of it once the scene is ready.
In a quiz, Clicky asks what that part is and what it does when the camera tour ends, and a correct name that misses what it does gets one follow-up.
The learner answers by voice.
`POST /judge-answer` asks Sonnet to grade that answer as correct, named only, wrong, or a request for help, and returns one spoken sentence.
If the judge call fails, the app falls back to the word match in `LiveSceneAnswerJudge`.
A finished scene stays above every window until Escape clears it.
A frame pop-out does not vanish when it clears.
`window.liveScene.returnToSource()` in `frame-popout.html` fades the labels, eases the camera back to its starting pose, and flattens the subject back into the frame exactly over the video rect in 0.8 seconds, then posts `returnFinished` through `liveSceneEvent`.
`LiveSceneOverlay` tracks this as `LiveSceneOverlayPhase` (`hidden`, `showing(isFramePopout:)`, `returningToSource`).
`clear()` on a frame pop-out starts the return, and the window hides on `returnFinished` or after a 1.5 second fallback.
A second `clear()` during the return, a new scene, or any non-pop-out page hides at once, and `clear()` on a hidden overlay does nothing.
`waitForReturnToFinish()` returns when the window has hidden, and every path that resumes a video Clicky paused awaits it first, so the subject lands in the still frame before the video moves.
That includes "stop the quiz", which clears the question's pop-out before `VideoQuizSession.stop()` and then plays the video with `resumeVideoAfterQuestion()`, a plain question or "stop the quiz" that cancels a scene build, a pop-out that fails to open, and "Sorry, I couldn't build that one."
"Stop the quiz" reads whether a scene was building before it resets the phase for an open question, so a scene asked for on another tab is cancelled too.
Every clear in `CompanionManager` goes through `clearTheLiveSceneAndReleaseTheBuddy()`, which also sends the blue cursor back to the mouse when a narration holds it on a part, since a narration cancelled mid-sentence may never release it.
Only `frame-popout.html` has `returnToSource` and `answerMoment`, so generated pages and `landmark-tiles.html` keep the old instant clear and plain reveal.
During a video quiz question, Escape skips the question, clears its pop-out, and plays the video on.
When the tour ends the overlay catches the mouse, a drag orbits the camera around the last stop, and a trackpad pinch zooms it.
The overlay never becomes key, so the pinch comes from the push-to-talk event tap, not AppKit.
The overlay is a nonactivating panel, so the page under it keeps the keyboard.
Before any public release, add a runtime block for WebRTC in dynamically created frames, add authentication and rate limits to the Worker (the `GET /v1/3dtiles/` route spends the Maps key for any caller, `POST /voice-command` is an open Haiku proxy like `/chat`, and `POST /live-scene` and `POST /picture-flows` spend the OpenAI and Opus budget for any caller), send video captions to /live-scene as a separate untrusted field instead of merging them into the learner's request, and pass part labels read from a generated page as sanitized untrusted data instead of putting them in the system prompt.
A simulation page's control labels and units, its challenge prompt, and its hypothesis are page text of the same kind, so name them in that pass too.

**Simulation ("let me try it")**: `liveSceneKind(for:)` returns `.simulation` for "let me try it", "let me play with it", "can I try it", "simulate this", and the bare "let me try" or "can I try" when it is the whole utterance (`asksToTryASimulation`).
A try phrase must end the utterance, with up to two of "out", "now", "please", "myself", "too", or "in 3D" after it, each with an optional comma, so "let me try that again" and "can I try this on my phone" build nothing, and neither do "Let me try to ..." or "how do I simulate this".
A simulation wins over "show me" and "in 3D" but not over a quiz, pop-out, or animate request.
With no scene on screen and no quiz question open, `handleTranscript` starts the experiment agent (`startTheExperimentInTheBackground`) straight away, ahead of the voice command router, so a demo never depends on a model choosing the tool, and Clicky says "Sure, I'll build that while you watch."
With a scene on screen the router reads it, since "can I try 60 degrees" means a slider.
`LiveSceneKind.workerRequestKind` is the one value that reaches `POST /live-scene` as `kind`, and a simulation is built by a background agent (`BackgroundAgentKind.experiment`, below), so the video keeps playing while it builds and pauses when the experiment rises out of it.
A simulation page is a science experiment: the prompt asks for the equipment the topic needs, a lab bench for a tabletop experiment and a grassy field for one that covers many meters, the standard simple model for the topic (projectile motion, torque balance, the pendulum period, Newton's law of cooling, buoyancy, Snell's law, Ohm's law, a rate that doubles for every 10 degrees Celsius, or electron-pair repulsion for a molecule's shape), the geometry that model's textbook formula assumes, and, for a rule-of-thumb model such as electron-pair repulsion, one free constant tuned so settled results match the textbook values.
Its rules are general, with a launched ball as the main example, so a new topic needs no paragraph of its own.
Over a screen that is not a science lesson, the prompt asks for the science behind what it shows instead of a copy of the app.
The page draws its own sky or lab room so the paused video never shows behind it, shows each instrument's reading and each material's state, sets each control's new setup without showing the result, animates each run as it happens (whatever moves, moves, a reading sweeps to its new value, and a traced path draws as it goes), and frames the equipment large with a camera that moves only for the tour, the voice tools, a drag, and the challenge, from a view where no part hides what a readout or a run depends on.
The challenge tolerance is about 3 percent of the target, or, for a readout with only a few separate values such as a molecule's angles, less than half the gap to the nearest other value.
It keeps the whole `window.liveScene` contract and adds `controls` (up to 3 of `{ name, label, min, max, step, value, unit }`, the variables), `setControl(name, value)` (clamps, applies, puts the run back at its start, false for an unknown name), `run()` (plays once from the current controls and returns a Promise that resolves when the run ends), `reset()`, `readouts` in `getState()` (`{ label, value, unit }`, the measurements, empty before the first run, rounded to 2 decimals), `setLabelsVisible(visible)` (part labels start hidden so they never cover the setup), `setPreviewVisible(visible)` (a setup with a path draws it as a dashed line that `setControl` redraws from the same physics the run uses, ending at a ring where the run will land, hidden until the guess), faded lines of the last 3 runs' paths, and `challenge` (`{ prompt, readoutLabel, target, tolerance }`) with `setChallengeVisible(visible)`, which marks the target and frames it.
The model never draws controls, and `liveSceneReply.ts` rejects a simulation page that lacks any of `controls`, `setControl`, `run`, and `readouts`, or that draws an `<input>`, `<button>`, `<select>`, or `<textarea>`, as markup or with `createElement`, so the retry-once path handles it.
The other primitives are optional, and a page without one loses only that step.
The quiz fields carry the lesson: `question` is the hypothesis, `answerLabel` the control it is about, `functionWords` empty, and `explanation` the why.
A simulation is not graded by the judge, so its phase ends at `.allLabelsShowing`, and after the tour Clicky speaks the hypothesis plus "What's your guess?" (`SimulationLesson.guessInvitation`).
The lesson runs in four stages that `scene-tools.js` owns (`lessonStage`): `guess`, where Run and the dashed path stay locked until the router's `record_guess` tool hears an answer (`clickyTools.simulation.guessHeard()`) or the learner clicks the locked button, which posts `guessSkipped`; `explore`; `challenge`, which the app starts with `clickyTools.simulation.startChallenge()` once the guess is settled, hiding the dashed path so the learner aims from earlier trials; and `done` after a hit.
`SimulationLesson.swift` holds Clicky's side: the guess, the run report parsed at the boundary (`SimulationRunReport`, with the last 5 trials and the challenge outcome), and every spoken line.
After each explore run Clicky says the readouts, then asks Claude, through the streaming `/chat` path with `simulationPredictionCheckSystemPrompt`, whether the trials answer the hypothesis.
While every trial so far used one setting (`SimulationRunReport.trialsTryMoreThanOneSetting`), Clicky skips that call (`simulationGuessCheckStep`), since one setting cannot answer a guess about a change.
It says `simulationTryAnotherSettingLine` on runs 1 and 2, and from run 3 it moves on with the page's explanation.
The reply starts with `[SETTLED]` (Clicky says whether the guess was right and why, in at most 35 words) or `[OPEN]` (what to try next), and after 3 runs the lesson moves on anyway with the page's explanation.
A failed check says the explanation.
Each challenge try gets `simulationChallengeSpokenLine`, and a hit plays "Glass".
`scene-tools.js` draws one panel on the document root once the tour ends (a slider per control, a Run button labeled "Say your guess" while locked, the hypothesis while Clicky waits for the guess (`clickyTools.simulation.showQuestion`), the readouts, the challenge line, and a results table of the last 5 trials, styled like the scene labels), and a press on it never turns the model.
The table's one measurement column shows the challenge's readout, else the first readout that has differed between trials, else the first readout, so a fixed control sample beside the test one never fills it.
The panel is opaque, and its readouts show "…" while a run plays, since they are still the run before's.
The panel covers the bottom of the view, so `keepSceneAbovePanel` moves the camera's view up with `camera.setViewOffset`.
The lift is half the height the panel reaches with a full trials table (`panelHeightWithAFullTable`), or half a taller panel's height, so the scene stays still as rows arrive.
The view offset keeps the scene and the labels the page projects in the space above the panel, and `keepSceneAbovePanel` applies it again after a resize.
The Run button and the `run_simulation` tool share `startRun()`, which posts `runFinished:<report JSON>` (`{ readouts, pastRuns, challenge }`) through `liveSceneEvent` when the run's Promise resolves, and ignores the end of a run a newer run replaced.
A run that rejects, throws, or has not ended after 20 seconds only unlocks Run, adds no trial, and posts nothing, since the readouts on the page are still the run before's.
`LiveScenePageEvent.simulationRunFinished` parses it at the boundary, cutting each label and unit to a short length and keeping at most 3 finite readouts, and `CompanionManager.narrateTheSimulationRun` speaks only while Clicky's own record says a simulation is on screen (`LiveScenePageOnScreen.simulation`), starting with `simulationReadoutSpokenLine` (no model call, for example "That run gave a landing distance of 40.84 meters, and a peak height of 10.2 meters.").

**Voice Commands**: A follow-up command spoken while a scene is on screen or a video plays in Chrome's front tab, on any site, goes to `POST /voice-command` instead of the keyword path (`voiceCommandRouterTakesTheTranscript`).
A quiz answer still goes to the judge, a scene still building keeps the keyword path, and "put it back" and "animate this" keep their own phrase matches ahead of the router.
The tools use the WebMCP and MCP shape (`{ name, description, inputSchema }`), but the page is a `WKWebView`, not Chrome, so they are plain functions the app calls with `callAsyncJavaScript`, not `navigator.modelContext`.
Page tools live in the bundled `LiveSceneAssets/scene-tools.js`, which the overlay adds to every page before its scripts run as `window.clickyTools` (`list`, `call`, `state`).
They are `rotate_model`, `zoom`, `zoom_to_part`, `reset_view`, `explode_view`, and `set_inside_view`, each listed only while the page has the primitive it needs, and every call ends the camera tour first, except on a landmark page before its reveal, which keeps locating and framing the place until then, and refuses a voice turn, zoom, or reset with "still loading", since the tour would put the camera back when it ends. A frame pop-out refuses them the same way while it builds or lands back in the video, so Clicky never confirms a change that did not happen.
`frame-popout.html` and `landmark-tiles.html` add `rotateBy`, `endTour`, `getState`, and `resetView` to `window.liveScene`, and their camera eases to a voice zoom or turn after the tour, or jumps there with Reduce Motion on. A voice turn on a pop-out of a picture that already shows depth stays inside the same limits a drag has, so the card never shows its edge.
Rule 7 of the `/live-scene` prompt asks generated pages for the same primitives plus `THREE`, `camera`, `renderer`, and `parts` (`{ label, object, isOuterShell }`), which `explode_view` moves apart and `set_inside_view` cuts open with a clipping plane through the model's center that follows the camera.
Page tools also include `set_control` (name and value, listed with the page's controls and their ranges in its description) and `run_simulation`, each listed only while the page has `controls`, `setControl`, and `run`, and `set_labels` (visible), listed only while the page has `setLabelsVisible`, with `labelsAreShown` in the state.
`pageVoiceToolNames` lets only those names through.
App tools (`AppVoiceTool`) are `answer_with_screen`, `build_new_scene`, and `pop_out`, which hand off to `respondToTranscript` (the old path), `build_simulation`, which starts the experiment agent like `build_model_in_background` starts a model, plus `record_guess`, offered only while a simulation waits for a guess, and `close_scene`, `explain_part`, `pause_video`, `play_video`, `seek_relative`, `seek_to_time`, `set_speed`, `find_moment`, `end_quiz`, `make_study_guide`, `revise_study_guide`, `open_study_guide`, `build_model_in_background`, `show_ready_model`, `start_background_task`, and `hear_task_answer`, each offered only when it can work.
The study guide tools are offered while a YouTube video is in front and no quiz question is open. ## CI

`.github/workflows/ci.yml` runs on every pull request and on pushes to main.
The `worker` job runs `pnpm test` and `pnpm run typecheck` in `worker/`.
The `bench` job typechecks `bench/` and checks that the committed results in `bench/results/` still parse.
It also runs `verify-clicky.test.sh`, which checks how `verify-clicky.sh build` tells that the app is older than a Swift file.
The `app` job builds the `leanring-buddy` scheme with Xcode 26.5 and `CODE_SIGNING_ALLOWED=NO`, then runs `leanring-buddyTests` hosted in the built `Clicky.app`.
Pushes and same-repo pull requests run it on the self-hosted runner `clicky-mac` on Chris's Mac, because GitHub's macOS queue can take over 10 minutes.
That runner runs as the separate `clicky-ci` macOS user and builds into the job's temp folder.
Chris's Screen Recording and Accessibility grants belong to the `Clicky.app` his Xcode builds, and CI never replaces that app.
The test host only checks those permissions and never requests them.
Chris's home folder must stay mode 700, so CI jobs cannot read his files or tokens.
The hosted tests need a desktop session to reach `testmanagerd`, so the runner starts from the login item `/Users/clicky-ci/Library/LaunchAgents/com.crodris.clicky-ci-runner.plist`.
After a restart, log in to `clicky-ci` once through fast user switching, then switch back, and the runner keeps running in that background session.
Chris has the `clicky-ci` password.
While the Mac sleeps or `clicky-ci` is logged out, these jobs wait, and GitHub cancels a job that waits over 24 hours.
On the Mac runner, a step fails the job when `xcodebuild -version` is not Xcode 26.5.
After updating Xcode, update every `26.5` in `ci.yml`, this file, and `README.md`.
Fork pull requests run on GitHub's `macos-latest`, and the repo requires approval before an outside contributor's workflow runs.
A fork can change `runs-on` or add a workflow, so never approve a fork run whose diff touches `.github/`.

## Code Style & Conventions

### Variable and Method Naming

IMPORTANT: Follow these naming rules strictly. Clarity is the top priority.

- Be as clear and specific with variable and method names as possible
- **Optimize for clarity over concision.** A developer with zero context on the codebase should immediately understand what a variable or method does just from reading its name
- Use longer names when it improves clarity. Do NOT use single-character variable names
- Example: use `originalQuestionLastAnsweredDate` instead of `originalAnswered`
- When passing props or arguments to functions, keep the same names as the original variable. Do not shorten or abbreviate parameter names. If you have `currentCardData`, pass it as `currentCardData`, not `card` or `cardData`

### Code Clarity

- **Clear is better than clever.** Do not write functionality in fewer lines if it makes the code harder to understand
- Write more lines of code if additional lines improve readability and comprehension
- Make things so clear that someone with zero context would completely understand the variable names, method names, what things do, and why they exist
- When a variable or method name alone cannot fully explain something, add a comment explaining what is happening and why

### Swift/SwiftUI Conventions

- Use SwiftUI for all UI unless a feature is only supported in AppKit (e.g., `NSPanel` for floating windows)
- All UI state updates must be on `@MainActor`
- Use async/await for all asynchronous operations
- Comments should explain "why" not just "what", especially for non-obvious AppKit bridging
